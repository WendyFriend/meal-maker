# Working conventions

- My Journal uses `client/MyJournal.tsx`, `client/journal/`, and `client/services/journalService.ts`. Entries snapshot the displayed meal portions and use local-day boundaries, not UTC calendar days. The table and RLS live in `supabase/migrations/202610290001_food_journal.sql`.
- Recipe Detail renames in place: the name becomes an auto-growing underlined `textarea` (no box; same font, width and lines as the heading; Enter saves, Esc cancels, line breaks become spaces) tied to a hidden form, and ✕ "Edit Name" ✓ appear in the app header via `onNameEditingChange` (the `page-header-create-recipe page-header-name-edit` header stays visible while typing on mobile). The + stays so nothing reflows.
- Saved meal edits are handled by `client/RecipeDetail.tsx`; `App.tsx` persists them with `updateRecipe` and passes saved overrides to the mounted My Meals list. Instructions editing lives in the shared `MealInstructions` component.
- My Ingredients and My Meals share `useCollectionSelection` and `CollectionSelection` controls for long press and bulk deletion. Keep both behaviours consistent.
- Recipe Detail, Create Recipe and Add Meal share one layout: name, a `NutritionOverview` with the `nutrition-overview-card` class (`MealResult` `summaryVariant="card"`), then `DetailTabs` (Ingredients | Key Nutrients | Steps; Add Meal has no Steps) with `DetailTabPanel` from `client/components/DetailTabs.tsx`. Keep tab names, order and card styling in those shared pieces. Entering edit mode must not move content: Recipe Detail keeps its header actions (+ or plan-meal ★) while editing ingredients or steps, the name stays the same (disabled) tappable block, section ✕/✓ overlap the 40px section header, and ingredient rows in edit mode pass `showChevron="space"` so the hidden › keeps names wrapping the same.
- My Plan "Add meal" (`AddRowButton`, shared with Add ingredient) opens `client/journal/AddMealSheet.tsx`, built on `components/ActionSheet` like the Add Ingredient sheet. Recipes are copied into a journal entry (no link back), so plan edits never change the recipe. "Create a new one" opens the `add-meal` sub-page: `CreateRecipe` with `subject="meal"` (Meal name, optional via `fallbackName`, no Steps) that saves to the plan only, never My Recipes. New meals use `nextPlanTime` and `defaultMealName` from `client/journal/planMeal.ts` so they are listed last.
- On My Plan, a collapsed meal expands from anywhere on its row, and its name chevron is hidden (`ingredient-name-chevron-space`, keeping the wrap). Once expanded, the name side (with the same `ingredient-name-chevron` as ingredients) is a button that opens the `plan-meal-detail` page and the trailing chevron column collapses it. Long press, right-click and Alt+Arrow are on the whole row (`journal-meal-row`). The page is `RecipeDetail` with `variant="plan-meal"` (parent My Plan): name and ingredient edits save back to the plan entry via `updateJournalEntryName` / `updateJournalEntryIngredients` (never to My Recipes; the name uses the same header ✕ "Edit Name" ✓ as Recipe Detail), steps are not editable, and MealResult's star saves a copy to My Recipes. Save toasts (star, Add to My Plan) appear on tap and are withdrawn if the request fails. Toast messages end with a full stop.
- My Plan ingredient edits save on leave (`client/hooks/useSaveOnLeave.ts`): a tap (not a scroll) outside the meal, collapsing it, another page or date, hiding the app, or unmounting saves like ✓, including a name still in the field; only ✕ discards. Surfaces opened from the edit (dialogs, popovers, listboxes, menus, toasts) don't count as leaving. While a meal is being edited its header shows only the name (not a link) and ✕ / ✓ (`journal-meal-row-editing`): no collapse chevron (✓ takes its column), no long-press reorder, and ✕ shows a "Changes discarded." Undo toast when something changed.
- My Plan meal order is gesture-only via `client/hooks/useLongPressReorder.ts`: long press lifts (items carry `data-reorder-id`), drag moves cards with direct DOM transforms (no per-move React renders), and drop saves immediately and optimistically, reverting on failure. No arrange mode or ✕/✓ bar; keyboard uses Alt+Arrow and the context menu offers Move Up/Down.
- List deletes are optimistic via `client/hooks/useUndoableDelete.tsx` (row collapse from `useRowExit` + shared `collection-row-exiting` CSS). Swipe-left (`SwipeableCollectionRow`, synchronous `onDelete`) and right-click (`CollectionContextMenu`) call `remove`, which shows the "Meal/Recipe/Ingredient removed" Undo toast and deletes only when it expires; confirmed bulk deletes use `removeNow`. Never await the server before animating a row out. Draft-only removals (Recipe Detail ingredient editing) use `useUndoToast` directly: Undo re-inserts at the original index, and the toast is dismissed on save, cancel or section change. My Plan, My Meals and My Ingredients share this.
- Add and Edit Ingredient share the form in `client/IngredientPage.tsx`; wrappers handle creating and updating saved records.
- Ingredient nutrition sheets share `NutritionDialog` and `NutritionSheetDialog`, backed by the reusable `client/components/SlidingSheet.tsx` and `.css` for modal focus/scroll ownership, draggable handles and exit transitions. Mount `SlidingSheet` while open and unmount it in `onClose`. Their edits to saved ingredients use `client/ingredients/IngredientCollectionContext.ts` to update App's existing ingredient state; keep chip and meal-result sheets consistent.
- Chips keep the name the user typed; ingredient nutrition sheets title the matched database food. The sheet is `NutritionDialog` (flows and state), with the menu in `NutritionFixMenu` and pure form logic in `nutritionForm.ts` (`nutritionForm`, `applyNutritionForm`, `ingredientFromFood`). `onNutritionResolved` only updates what is shown; never reset an open form from it. A small ? icon after the title's last word (`titleAccessory`, labelled "Doesn’t look right?"; kept on that line by a word joiner and a `nowrap` row, centred on the capitals with a measured `vertical-align`) opens a menu captioned "Not the ingredient you entered?" in the shared `client/components/Popover.tsx` (native `popover="auto"` light dismiss, also behind `NutritionInfo` micronutrient popups) with: Choose a different food (`FoodMatchPicker` in a full-height sheet via `NutritionSheetDialog` `fullHeight`, so loading never resizes it; Nutrition Lab food search prefilled with the typed name; a pick keeps the typed name, sets `resolvedName`/`nutritionSource`, and marks missing micronutrients unavailable so the old match's lookup never fills them), Scan nutrition label, Take a photo (vision model names the food, then the picker searches it), and Correct the numbers. The same menu also sits under Vitamins & minerals ("The numbers don’t look right?"). Correct the numbers edits macros and micronutrients in place, starting from the values on screen when editing begins (nutrition can arrive after the sheet opens, so never rely on values captured at mount): no hint is added, the links leave hidden placeholders, and the soft filled fields use negative margins so no row moves (keep it that way); the title stays read-only and the sheet header is sticky so ✕/✓ stay reachable. A cleared micronutrient is saved as unavailable, and `unavailableMicronutrients` always shows N/A even when a lookup has a value. Photo requests go through `client/services/nutritionPhotoService.ts` to `/api/nutrition-label` and `/api/identify-food`, which share `server/ai/vision.ts` (`OLLAMA_VISION_MODEL`, else `OLLAMA_MODEL`). Label scans convert per-serving or kJ readings to per-100g, only fill the form for review, and omit unread values rather than zeroing them.
- Database schema changes live in `supabase/migrations/`. Custom ingredient preparation tips use the nullable `user_ingredients.preparation_tips` text array; existing rows fall back to shared suggestions.

- Keep header edit and save buttons keyed separately and prevent the edit click’s default action, so a trusted click cannot immediately submit the newly rendered save button.
- Use `client/utils/nutrition.ts` for portion-based macro totals and `useModalDialog` for native modal focus/scroll lifecycle. Date boundaries stay in `client/journal/nutrition.ts`.
- Detail-page edit pencils belong in the app header. Ingredient and meal pages expose `DetailEditorHandle` refs; Meal Details is read-only until header editing starts. Use `SelectIcon` for list selection, reserving the pencil for editing.
- Use `client/components/ActionFeedback.tsx` for brief centered action confirmations; My Day add/remove share this modal and `MyDayIcon` (+/−).
- Use `CancelButton` (bare ✕, leading) and `ConfirmButton` (bare coral ✓, trailing; no circle backgrounds; `busy` shows the spinner, `tone="danger"` for destructive confirms) from `client/components/ConfirmCancelButtons.tsx` for every cancel/done/save pair, following Apple's HIG. Don't use text Cancel/Done buttons. Sheet close buttons keep their own ✕; "Select" stays text.
- Use `client/components/ResetIcon.tsx` for reset controls and give icon-only buttons an accessible name and tooltip.
- Use `client/components/LoadingSpinner.tsx` for loading indicators, with status text on the container. It shares styling and reduced-motion support across the app.
- Use `client/components/EditIcon.tsx` and the `edit-icon-button` class for edit controls, matching My Ingredients.
- Create Meal state stays in App; `MealMakerForm` composes the controls. Control styling belongs in its own CSS (`IngredientInput`, `QuickAddIngredientPicker`, `Calories`, `SelectedIngredients`); shared field/heading styling belongs in `MealFormField.css`. Avoid restoring duplicate form-scoped control overrides in `MealMaker.css`.
- Reuse existing shared components and tokens. Nutrition content styles belong in `IngredientNutritionContent.css`; generic sheet positioning/gestures belong in `components/SlidingSheet`; ingredient sheet controls belong in `IngredientNutritionSheet.css`.
- The detail page uses an `h1` and the sheet an `h4`. Keep their shared title typography explicit, including letter spacing, so global heading rules do not make them diverge.
- Nutrition records are per 100g. Meal totals and ingredient contributions multiply by ingredient weight / 100. Missing data is different from a genuine zero.
- Keep ingredient identity and preparation form intact during food matching. Micronutrient lookups are shared and cached between meal and ingredient views. The shared `RecipeIngredientNameInput` (Create Recipe, Recipe Detail and My Plan ingredient editing) prefetches the lookup after a 250ms typing pause via `usePrefetchIngredientNutrition`; committing reuses the in-flight request. On focus it calls `client/utils/revealAboveKeyboard.ts`, which keeps the field and its first suggestions above the on-screen keyboard (via `visualViewport`) and adds the keyboard height as temporary scroll room (`--keyboard-inset`, a spacer after `.page-transition`). `server/nutrition/lookupFood.ts` caches matches in memory per name for 24h (failures are not cached; tests call `clearFoodLookupCache`).
- `IngredientNutritionContent` owns the shared food/nutrition lookup and passes its state to `IngredientNutritionDetails`; the header image reuses the supplied or looked-up food ID. Request a missing food source for images unless the ingredient came from Nutrition Lab generation (`thumbnailSource: 'nutrition-lab'`).
- Nutrition Lab is the only nutrition and meal-generation provider (the Ollama/USDA pipeline and its Settings choice were removed; Ollama remains only for vision via `server/ai/vision.ts`). Nutrition Lab generation sends valid macro fields directly alongside each ingredient name; do not nest them in `match` or require a food ID. Send available micronutrients as a sparse `micronutrientsPer100g` object, preserving zeros and omitting unknown values. NL fills missing values; explicit response nulls remain unavailable and should not trigger another lookup. Use NL's returned macros for meal totals so they match its portion sizing.
- Preserve unrelated working changes. The repository may contain substantial uncommitted UI work.

# Focused validation

- CSS/copy changes: targeted Prettier check and `git diff --check`; use a browser preview when layout needs confirmation.
- Client TypeScript: `npm run typecheck:client`.
- Server TypeScript: `npm run typecheck:server`.
- Shared types or cross-layer changes: `npm run typecheck`.
- Changed TS/TSX files: `npm run lint:files -- path/to/file.tsx` (pass explicit paths).
- Production bundling, asset, import or build-config changes: `npm run build:client` or `npm run build` as appropriate.
- `npm run test:client` runs the complete frontend suite; `npm run lint:client` checks all frontend files.
- Run relevant tests for behavior changes when needed. Reuse passing checks until another change or unresolved concern justifies repeating them.

Incremental TypeScript and ESLint caches live under ignored `node_modules/` paths. Development API startup uses `npm run server` without a frontend production build; run the frontend separately with `npm run dev`.
